# LIBERO-PRO 2.0 Local Deployment Package v1.0.0

These scripts support offline Docker deployment on Ubuntu 22.04 x86_64 NVIDIA hosts. The current
source includes 1688 task instances, initial states, and perturbation implementations. The HF
evaluation package described in the root README is recommended. For offline Docker deployment,
first build and export an image from the current GitHub checkout, then use these scripts.

## Host requirements

- Docker Engine and Docker Compose v2
- NVIDIA drivers and NVIDIA Container Toolkit
- Recommended: 16 CPUs, 32 GB RAM, 8 GB GPU memory, and 100 GB SSD
- The initial version supports Linux x86_64 only and binds to `127.0.0.1:8000` by default

## Installation

```bash
# Build the offline delivery directory from the repository root after downloading all Git LFS assets.
git lfs pull
docker build -t libero-pro-server:1.0.0 .
mkdir -p docker-delivery/images
cp -a deploy/customer-local/. docker-delivery/
docker save -o docker-delivery/images/libero-pro-server-1.0.0.tar libero-pro-server:1.0.0
cd docker-delivery
sha256sum images/libero-pro-server-1.0.0.tar > SHA256SUMS
bash install.sh
# In the model environment, install the lightweight client from the downloaded source.
python3 -m pip install -e /path/to/LIBERO-Pro2.0
set -a && source client.env && set +a
python3 smoke_test.py
```

`configure.sh` generates a random API key and a separate result-signing key. Only the API key's
SHA-256 hash is saved in the server `.env`. For a fully offline target, prepare a client wheelhouse
with its dependencies separately; image building and initial dependency downloads require network access.
Before starting the service, `install.sh` also verifies NVIDIA GPU access from the Docker container.
If that check fails, repair NVIDIA Container Toolkit before continuing.
Do not share `.env`, `client.env`, or runtime databases. If the model runs on another LAN host,
change the Compose port binding to `0.0.0.0:8000:8000` and restrict firewall access to designated
LAN source addresses. Do not expose the service directly to the public Internet.

### HTTP across LAN hosts

When the model and LIBERO service run on different hosts, configure the LIBERO server's firewall
to allow only the model server's LAN source address to access TCP 8000, then configure and install:

```bash
export LIBERO_REMOTE_BIND_ADDRESS=0.0.0.0
export LIBERO_REMOTE_PUBLIC_URL=http://LIBERO_SERVER_LAN_IP:8000
bash install.sh
```

Replace `LIBERO_SERVER_LAN_IP` with the LIBERO server's LAN IP reachable from the model server.
`configure.sh` writes it to the server `.env` and the first account's `client.env`; subsequent
account files generated by `add_account.sh` inherit the same address. Securely give each account
its own `client*.env`, then run on the model server:

```bash
python3 -m pip install --no-index --find-links wheels wheels/libero_remote-1.0.0-py3-none-any.whl
set -a && source client.env && set +a
python3 smoke_test.py
```

HTTP Bearer keys do not encrypt transport. Do not expose port 8000 directly to the public Internet;
use a VPN, tunneling service, or HTTPS gateway for public-network access, and continue restricting
allowed source addresses.

Add an independent account:

```bash
bash add_account.sh team-b
docker compose up -d --force-recreate
```

The script generates `client-team-b.env`. Give each account only its own file; do not share API keys.
For concurrent accounts, set `LIBERO_REMOTE_MAX_SESSIONS` in `.env` to the total environment capacity
the server can sustain. `LIBERO_REMOTE_MAX_ACTIVE_SESSIONS_PER_OWNER` limits each account's occupancy.
Keep total concurrency within GPU memory and host RAM capacity.

## Model integration

```python
from libero_remote import RemoteLiberoEnv

env = RemoteLiberoEnv(
    base_url="http://127.0.0.1:8000",
    api_key="LIBERO_REMOTE_API_KEY_FROM_CLIENT_ENV",
    timeout=120.0,
)
obs, info = env.reset(
    suite="libero_goal",
    task_id=9,
    init_state_id=0,
    seed=142,
    variant="S10",
)
terminated = truncated = False
while not (terminated or truncated):
    action = model.predict(obs, instruction=info["language_instruction"])
    obs, reward, terminated, truncated, info = env.step(action)
result = env.result()
env.close()
```

Models are not limited to xVLA. Use the Gym-style interface directly or implement an `AgentAdapter`
for any PyTorch, JAX, TensorFlow, ONNX, private inference API, or traditional policy. The server
validates only standard observations/actions and authoritative environment results.

## Current task coverage

- 4 suites: `libero_goal`, `libero_spatial`, `libero_object`, and `libero_10`
- 40 official base tasks; the release includes 40 BASE, 863 static, and 785 dynamic instances
- 1688 valid BDDL files in the release manifest; evaluate only applicable combinations present in it
- `/v1/tasks` is the sole source of available suite/task/variant combinations; clients must not assume a Cartesian product
- Fixed `init_state_id + seed`, with task, initial-state, first-observation, and perturbation-plan fingerprints returned
- `relative` and `absolute` 7D actions, with exact shape/range defined by `info["action_schema"]`
- Direct sessions and persistent run/lease scheduling as client options

## Multiple users and reproducibility

Each account must use a distinct API key; configure accounts with `add_account.sh`. Sessions, runs,
leases, and results are isolated by account and subject to per-account active-session quotas.
Repeated evaluations must keep BDDL, initial state, environment seed, camera parameters, control
mode, model checkpoint, processor, and model seed fixed. The server checks five environment-side
fingerprints and records the action hash chain.

## Local deployment limitations

The local package supports development, private evaluation, and public reproduction. Users can
modify local images and evaluation logic, so local results are not tamper-proof leaderboard
evidence. The service does not upload user models, weights, or API keys.
